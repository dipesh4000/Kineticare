# Assessment foundation

Clinicians open **Patients → Open patient → Clinical assessment → Add assessment**. The sectioned form supports anthropometrics, posture, bilateral shoulder abduction/knee flexion ROM, quadriceps strength, pain by site, restrictions, functional tests and notes. Blank fields mean not assessed, not zero or normal. BMI is computed on the server; somatotype is descriptive only.

Publishing creates an immutable record in the existing MongoDB `patientRecords` collection with `kind: assessments`. The key is `patientId:assessments:assessmentId-vN`. Server-owned patient/clinician identities, publication status, creation time and predecessor are added by the API. Enum values are shared between the form and strict Zod validation. Unknown fields, invalid enums, invalid numeric values and nonconsecutive versions are rejected. Duplicate publication returns 409, including competing requests for the same version. There is no update/delete endpoint for published assessments.

`POST /api/records/:patientId/publishAssessment` accepts `assessmentId`, `version`, `assessedAt` and the form sections. Version 1 starts a record series; later versions must have a published predecessor owned by the same clinician for the same patient. `GET /api/records/workspace` includes `assessments[patientId]`. Only clinicians with current patient consent may publish or read clinician records; patients may read their own assessment history (also after revocation). Other clinicians cannot read assessments from a previous treating clinician. Authorization uses the existing Privy identity and Atlas relationship checks; no Firestore rules are involved.

The assignment screen requires a published assessment before publishing a new plan. A draft can be saved without one. Assessments older than eight weeks trigger a warning, without blocking clinician judgment. Existing legacy plans remain usable. Each new assignment stores the exact `assessmentId` and `assessmentVersion`; no automatic target changes are made in this stage.

Workout drafts capture both assignment and assessment versions at start. Session saving resolves the exact published assignment on the server and rejects mismatched assessment pointers. Reassessment does not rewrite prior assignments or sessions. Legacy/self-guided sessions store null assessment pointers and an explicit fallback evaluation basis. Movement reports show the recorded baseline version or explain that no baseline is recorded. Analytics prefers recorded exercise targets over a newer plan’s targets, preserving historical evaluation context.

This stage records baselines and provenance. It does not automatically derive exercise rules, enforce restrictions in the rep engine, calculate ROM change against clinical measurements, or produce symmetry measurements. Approximate 2D camera excursion is not treated as interchangeable with clinician-measured ROM. Personalization, logged target overrides and baseline progress calculations are the next stage; pain check-ins, reminders and the wider roadmap remain separate work.

Validation: `npm run test:backend`, `npm test`, `npm run lint`, `npm run build`. Assessment tests cover strict validation, calculated BMI, partial data, access denial, immutable versions, predecessor links, assignment baseline selection and preservation of session pointers after reassessment.
